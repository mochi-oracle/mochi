# Remaining protocol wait windows

Survey as of 2026-09-30. These windows are unchanged by the short admin timelock and attestation recovery release. New timelocks default to 60 seconds; deploy/launch/batch/owner tooling accepts only 0–3600 seconds. Existing contracts keep their deployed parameters. The OpenZeppelin controller itself permits governance to update its minimum delay; tooling bounds are not an immutable contract cap.

| Window and location | Can a customer review wait? | Can launch/admin/recovery wait? | Recommendation |
|---|---|---|---|
| Panel commit 24 h, reveal 24 h, appeal 24 h: `contracts/src/PanelEscalation.sol:25–27`; `reveal`, `resolve`, `appeal`, `finalize` | Yes, an escalated case can wait through commit/reveal and the first-panel majority appeal window; an appeal repeats commit/reveal. `reveal` can start early once all panelists commit and `resolve` can run early if everyone reveals; missing participants can consume the full windows. Ordinary enclave reviews do not use these windows. | Not required for launch or attestation recovery; settling an existing panel case can wait. | Owner should decide shorter panel windows and an explicit customer escalation SLA; preserve fair reveal/appeal access. |
| Panel evaluator unstake 7 days: `contracts/src/PanelEscalation.sol:28`, `requestUnstake`, `withdrawStake` | No verdict wait; it delays an evaluator’s USDG withdrawal. | Funding withdrawal or evaluator retirement can wait; replacement enrollment does not require withdrawal. | Retain until the owner reviews evaluator liability and withdrawal policy. |
| ClerkVoting voting 3 days + execution 1 day: `scripts/deploy-local.ts` VOTING_PERIOD/EXECUTION_DELAY; `contracts/src/ClerkVoting.sol` constructor, `createProposal`, `queue`, `execute` | Existing active schemas/mixes remain usable; a review needing a newly voted schema/mix can wait. Voting also locks the voter’s stake until the voting end. | Schema/class-mix administration through ClerkVoting can wait at least four days; launch and attestation recovery do not require a vote. Timelock governor access is a separate path. | Decide whether to shorten the voting path separately; do not route emergency recovery through ClerkVoting. |
| MochiStaking unstake cooldown 7 days: `scripts/deploy-local.ts` MochiStaking constructor; `contracts/src/MochiStaking.sol` `requestUnstake`, `withdraw` (and vote locks) | No review/verdict wait; delays a staker’s MOCHI withdrawal. | Stake retirement/funding withdrawal can wait, not enclave launch or restart. | Retain pending a withdrawal/liability decision; account for vote locks. |
| MochiStaking reward stream 7 days: same deployment constructor; `contracts/src/MochiStaking.sol` `notifyRewardAmount`, reward accrual | No review wait; USDG staking rewards accrue over the stream. | Reward realization can wait; not launch/admin recovery. | Retain unless the owner changes reward distribution policy. |
| JurorRegistry exit 7 days: `scripts/deploy-local.ts` JurorRegistry constructor; `contracts/src/JurorRegistry.sol` `requestExit`, `withdrawBond` | No direct review wait, but exiting keys become inactive immediately; insufficient remaining seats can prevent service. | Bond withdrawal/retirement waits; adding replacement keys and restoring expired attestations do not wait on exit. An exiting key is never allowed through the expired-only startup exception. | Plan spare seats; retain the liability window pending an owner decision. |
| Schema activation delay, configurable without a one-day cap: `contracts/src/SchemaRegistry.sol` constructor/`setActivationDelay`/`propose`; `scripts/deploy-local.ts` SCHEMA_ACTIVATION_DELAY | A review needing a pending schema can wait; older active versions remain valid. | A newly required schema can block launch or schema repair if a long delay was configured. Current script deploys mainnet-style schemas with zero activation delay; local default is also zero. The interface’s historical “24h” comment is not a constructor default. | Keep zero for the launch; review any future nonzero setting explicitly and consider a bounded policy separately. |
| Timeout-slash interval 1 day: `contracts/src/JurorRegistry.sol` TIMEOUT_SLASH_INTERVAL, `slashTimeouts` | No review wait; rate-limits repeated timeout penalties. | Penalty administration can wait, not restart. | Retain as a penalty rate limit. |
| Feed subscription 30-day units: `contracts/src/Feeds.sol` `subscribe`; `contracts/src/interfaces/IFeeds.sol` | No mandatory wait: subscription becomes usable immediately and lasts the purchased duration. | No launch/recovery wait; expiry requires renewal. | Retain and monitor renewals. |
| Stock-token metadata effective date +1 day: `scripts/register-stock-tokens.ts` effectiveDate; `contracts/src/StockTokenCrosscheck.sol` ±1-day effective/ex-date tolerance | No built-in sleep; date mismatch can reject a financial crosscheck. | Registration metadata can misrepresent the intended activation date; not an enclave restart gate. | Review effective dates before running this separate registration tool. |

The one-hour QueryEscrow query TTL (`contracts/src/QueryEscrow.sol:42`) is not a multi-day window, but an outage can leave a paid query waiting for expiry/refund. It remains unchanged; expiry requires block time strictly after the deadline and a successful transaction. Rehearsal 7 used a held payment: prepare without submission while active, immediately deploy standby, verify remaining intake attestation validity, then simulate and submit once, pause, simulate early expiry, and expire after the deadline. This release does not execute that test or shorten customer refund timing.
