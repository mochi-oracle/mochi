# Claim review payments: readiness and implementation plan

> **Update, September 29, 2026:** the launch tariff is now **$0.10** for the short N3 review at `tokensK = 1` (jurors $0.08, minimum protocol fee $0.02; `scripts/launch-pricing.ts`). The testnet dress rehearsal measured about 918k gas of protocol-side settlement per review (seal + post), roughly $0.05 at mainnet gas, which five cents could not cover. Five-cent figures below are historical.

## September 28 implementation update

The private claim-to-protocol SDK bridge is implemented in `packages/sdk/src/claims.ts`. It commits a canonical claim/evidence document, marks supplied excerpts as SUBMITTED rather than independently fetched, and uses the established intake, encryption, quote, escrow and sealed-answer lifecycle. The browser integration is implemented with a saved private recovery file, a one-shot payment attempt and resume-without-payment. This advances steps 3 and 4 below; it does not establish production settlement readiness.

The latest source-quality audit covers 12 hand-selected cases and 36 paid inference requests, including the invalid fixture: eight cases resolved correctly, four remained unresolved, and three provider calls failed. A separate corrected-context case also remained unresolved. Its $0.01586906 reported-token estimate is partial, not actual billing; failed calls without usage have unknown cost. See `CLAIMS-LIVE-VALIDATION.md` and `CLAIMS-LAUNCH-PACKAGE.md` for scope, settlement outcomes, and cost limits. This is not the blinded independent production benchmark required below.

The five-cent target remains approved. Production tooling requires the team's later token address and never creates a production token. Review-funded purchases remain disabled; developer/creator fees remain outside their accounting. The earlier plan below describes remaining acceptance requirements as well as the original implementation gap.

## Original gap and protocol constraints

The claim research pilot is deliberately unpaid. `services/claims/src/app.ts` exposes research, review, publish, and public-share routes. Its config response advertises `$0.00`, requests an access token, and it has no wallet, payment, escrow, or chain dependency. `services/claims/README.md` explicitly says reviews do not produce TEE attestations or chain receipts and that five cents is only a target.

The separate production protocol is real but serves a different request shape. `packages/sdk/src/client.ts` prepares document intake and a query transaction through the gateway; `services/gateway/src/app.ts` encodes `QueryEscrow.openWithUSDG` or shielded openings; `services/gateway/src/main.ts` supplies the chain relayer path. `contracts/src/QueryEscrow.sol` escrows payment and `MochiVerdicts.post` is the trusted settlement caller. On verdict, escrow credits responding jurors and routes the protocol-fee residual through the existing staking/panel waterfall. The standalone claim review produces neither the signed provenance nor the encrypted/attested verdict inputs expected by that protocol.

Consequently, neither a live research pilot nor a successful on-chain document query proves that claim reviews can charge or settle. No paid-claim readiness checker is appropriate until a bridge exists: public deployment JSON cannot prove provider spend limits, review-evaluation quality, live attestation, or that a claim review actually settles.

## Required bridge

Implement this as a dedicated claim-review integration with its own request type and an adapter into the established gateway/escrow lifecycle. Do not bolt a second wallet/ledger or direct token transfer onto `services/claims`.

1. **Define the paid product and evaluate it.** Freeze the short-review scope, evidence/source limits, refusal and insufficiency behavior, and whether unresolved 2-of-3 results are charged. Run a blinded benchmark of independently reviewed claims using the intended real provider/model configuration. Record correctness, abstention, citation validity, latency, and per-review provider cost. Synthetic browser fixtures are UI tests, not this evaluation. Set provider spending caps before inviting external paid users.
2. **Define charge semantics and pricing.** Specify whether payment is collected at request creation or only after a completed review, and make timeout, provider failure, invalid output, duplicate request, and user cancellation outcomes explicit. Quote the five-cent target against measured worst-case compute and settlement costs. USDG has 6 decimals in the current token path, so five cents is `50000` base units; never use floating point. The escrow's current price formula is based on schema, juror classes and token count, not a fixed cents-per-claim product. Add an explicit, governed price/schema mapping or a purpose-built escrow operation only after tokenomics review.
3. **Create a privacy-safe claim query envelope.** Adapt the claim payload to the protocol's committed input model. Preserve the raw claim and evidence handling guarantees: do not put document text, private source passages, access tokens, or provider keys in chain calldata/events/logs. The protocol's `docCommit`, provenance, schema version, intake signature, payer/refund fields, nonce, visibility/disclosure flags, and result encryption must be bound consistently. Define what public claim reviews reveal before enabling the pilot's current public-share feature for paid reviews.
4. **Connect the existing lifecycle.** Add a claims adapter that obtains/verifies attested intake and juror responses, asks the gateway to prepare/open an escrow query, and stores the query ID against the claim review. The paid review must use actual on-chain payment (USDG or an already-supported shielded/voucher path), then seal and submit a valid `MochiVerdicts` result so `QueryEscrow.settle` distributes/refunds funds. A database “paid” flag, token transfer outside escrow, or a successful research response is not settlement evidence. Retries must be idempotent by request/query ID and recover from a chain transaction succeeding before local persistence.
5. **Keep revenue streams distinct.** The existing QueryEscrow settlement sends juror fees to operator claimables and splits protocol fees between panel reserve and staking rewards; it has no creator-fee concept. If review-funded purchases should fund product credits or manual $MOCHI burns, specify their source, accounting, custody, authorization, and reconciliation separately. Add a reviewed governance-controlled treasury/manual burn operation (or a separately audited purchase/redemption component) without subtracting from or relabeling creator/juror fees. Burns should be explicitly initiated and reconciled; do not imply that purchases automatically burn tokens. Document supply accounting and emitted evidence for each action.
6. **Operational rollout and production acceptance.** Wire configuration through the existing deployment/gateway conventions, verify production chain ID and the non-rehearsal contract deployment, token decimals/address, escrow wiring and pause state, active schema and prices, intake/juror/consensus attestor roles, relayer permissions, and USDG funding/allowance. Exercise successful verdict, hung/refund, timeout, duplicate/retry, and failed-provider cases on a rehearsal deployment. Then canary a single live claim, independently inspect the transaction and settlement events/claimables/refunds, compare provider and chain costs, and reconcile accounting before enabling a paid cohort. Never enable a paid claim route while any required settlement check is unavailable.

## Concrete code touchpoints

- `services/claims/src/app.ts`: paid route/config contract, request idempotency, explicit payment/settlement states, and safe errors. Keep existing unpaid pilot behavior until the paid path is enforced.
- `services/claims/src/review.ts` and `services/claims/src/types.ts`: review result and deterministic failure/abstention semantics consumed by the bridge; do not treat model agreement as attestation.
- `services/gateway/src/app.ts`, `services/gateway/src/ports.ts`, and `services/gateway/src/main.ts`: introduce the claims-specific input adapter only if current generic intake/provenance types cannot represent the bound claim request; route payment via the existing escrow.
- `packages/sdk/src/client.ts`: expose a claims-friendly prepare/pay/wait method only after the gateway and protocol contract shape is settled. Existing methods support the attested document query lifecycle, not the claims HTTP review API.
- `contracts/src/QueryEscrow.sol` and `contracts/src/interfaces/IQueryEscrow.sol`: only change if the accepted pricing/charge semantics cannot be expressed by current quote/open/settle methods. Preserve juror/operator and protocol-fee separation.
- `contracts/src/MochiVerdicts.sol`: settlement currently depends on a protocol-valid verdict; claims must provide the required signed/attested inputs rather than bypass this call.
- `services/claims` storage schema/migrations: persist payment intent, chain/query ID, transaction state, and reconciled settlement outcome without storing secrets or private evidence bytes.
- Deployment and operations docs: add production deployment verification and manual purchase/burn reconciliation after the contract and accounting design is approved.

## Readiness gates

The pilot is **research-ready only** when its configured providers and access controls are intentionally enabled. Paid claims remain **not ready** until all are true: real-model benchmark reviewed; provider spend limits set; five-cent economics validated; claim-to-protocol bridge implemented; payment is enforced by QueryEscrow; valid verdict settlement/refund is observed; duplicate/retry recovery works; manual purchase/burn accounting is separated from creator/juror fees; production deployment and roles are independently verified; and one live canary is reconciled end to end. Deployment metadata alone is insufficient to pass these gates.
